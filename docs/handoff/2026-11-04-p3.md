## 1. 旧方式との基準比較（構造比較）

旧方式 = 本体の Pipeline Studio 経路（設計正本 `spec/task-pipeline-design-2026-10-22.md`、
定義契約 `capabilities/contracts/pipelines.ts` の `pipelineDefinitionV1`、検査
`api/domains/pipelines/service/check.ts`、制作基盤 `service/works.ts`・
`application/pipelines/`、実行 `agent-runtime/service/execution-pipeline.ts`）。

| 観点 | 旧方式（本体） | 新方式（本 repo、契約 p0-2） |
| --- | --- | --- |
| 制作の場 | 協働型の専門セッション `pipeline.studio` が作業文書 `pipeline.json` を revision 管理で編集。利用者も画面から編集でき、不正なテキストは拒否ではなく「反映できなかった案」として指摘つきで保存される | 依頼ごとに制作AIが1回限りの定義を生成（bench では盲検生成＋記録再生）。公開・再利用の概念は初版に無い |
| 制作時に見える情報 | 手順に使える担当の一覧（id・題・要約300字・実行種別・instant の引数名。session / task / pipeline は除外）と、現在の検査の指摘を**毎ターン**渡す（検査つき対話ループが組み込み） | 部品カード24件を一括提示（入口・目的・使う/使わない場面・引数 schema・出力 schema 参照・副作用・確認）。検査の指摘は返さない（修復ループは別途 bench で測定） |
| 定義の目的と形 | 公開して再利用する toolchain そのもの。`id`・`title`・`summary`・`useWhen`・`avoidWhen`（候補提示の routing 情報）を持ち、`formatVersion: 1` | その依頼専用の手順。`request`・`steps`・`output` のみ。routing 情報は持たない |
| 入力の扱い | 型付き `inputs`（型・必須・既定値・enum・範囲、最大8件）を宣言し、実行時に初回ラウンドが利用者の依頼から当てはめる | 入力宣言なし。利用者の資料は `request` 参照に同梱され、手順の `from` で受ける |
| 手順の種別 | 2〜8件。toolchain step と extract step（前段のテキストから型付き値を1つ取り出す専用種別、schema で検証） | 1〜8件（下限が違う: 単一作業も定義できる）。全て部品への手順で、型付き変換の専用種別はない |
| 参照・受渡し | 文字列テンプレート `${steps.<id>.summary}` / `${inputs.<name>}` を request・arguments・answer に埋め込み実行時に展開。materials は text/value/request/prompt/reference/result/image/music の判別共用体 | 構造化された `from`（`request` か前手順 id の配列）のみ。式・加工はない。`arguments` は instant 入口のみ、リテラルの JSON オブジェクト |
| 定義内テスト | 定義に `tests`（発話・入力・偽の手順結果・期待値）を内蔵でき、fixture 運転が公開前の確認手段 | 定義にテストは持たない。評価は外付けのケース集合（`data/cases`）で、gold は制作側へ一切渡らない |
| 検査 | 2段＋公開条件: `checkText`（形式のみ、JSON Pointer + rule、最大16件）→ `checkPipeline`（参照・前方参照・予約入力名・範囲・toolchain の実在と実行種別・instant 引数の必須/未知・tests の整合。最大32件、値は含めない）→ 公開時に `useWhen` の例3件以上＋bundle の dry-run import | `checkDefinition` 1段: schema・重複/予約 ID・未知 bundle・未公開入口・参照漏れ・前方参照・循環・arguments の公開契約適合（変換できない schema は `arguments_unchecked` 警告として明示）。全指摘に path + message。制作状態は `AuthoringOutcome`（ready / needs_input / unsupported）で分離 |
| 失敗の扱い | 実行は `stepFault`（未完了・必須パス欠落）で停止し、run は partial として fulfilled / missing を返す。extract には修復1回がある | bench の実行は未採用で停止し後続を実行しない（P1 で部分試験済み）。機械的失敗への修復1回は Wave C で測定済み（13/13 回復・意味変化なし） |
| 実行への受け渡し | 公開 = toolchain の新 revision として bundle 登録。以後は通常の候補提示で選ばれ、agent-runtime の親実行が駆動する | 公開の概念なし。`PipelineHost` 経由で本体の子実行へ直接写像（P2 で写像と採用規律を検証済み。実 dispatch への結線・main 取り込みは承認後） |
| 証跡・評価 | work の revision / version 履歴、rejected draft、公開 revision、実行 record はあるが、「依頼→定義→検査→実行→評価」を1件に束ねた記録様式はない。検証は固定試験（domain verify 929件等）と studio の trial（順位 probe・初回ラウンド select 試行）が中心で、ケース集合による制作成績の測定はない | 作業DBに run / trial / check / mock / score を追記専用で記録し、ケース・split・版と対応付く。本 P3 の export で第三者検証が可能になった |

### モデル対照測定は公正に組めない（実施せず）

| 理由 | 内容 |
| --- | --- |
| 課題が違う | 旧は「再利用可能な toolchain 定義（routing 情報・型付き inputs・内蔵 tests まで）」の制作、新は「一回限りの手順定義」の制作。旧形式の gold を用意しても、測る能力が同一にならない |
| 制作面を再現できない | 旧の制作は協働セッションの対話ループ（毎ターンの担当一覧＋検査指摘＋作業文書の revision 管理）で、制作指示は製品DB内の bundle 登録（`pipeline-studio.bundle.json`）側にある。この clone のソースだけでは固定 snapshot として bench に持ち込めず、近似再現は再現度自体が交絡になる |
| 採点観点が揃わない | 旧の合否は checkPipeline＋公開条件＋内蔵 tests の fixture 運転、新の採点は状態・部品・受渡し・mock 完了。共通観点への写像を先に設計しないと、並べた数字が意味を持たない |
| live の条件 | 旧経路を実走させるには本体サーバーの起動が要り、規則上利用者の許可が前提（本作業では行わない）。旧側にも同条件の測定記録はなく、固定試験の数字だけが存在する |

対照測定に不足する条件（揃えば組める）:

1. 旧 studio の提示面（担当一覧の作り方・指摘の渡し方・制作指示文）の固定 snapshot を bench へ持ち込めること。
2. 共通ケースに対する旧形式 gold（inputs・steps・answer の許容集合）と、共通採点観点（部品選択・受渡し・実行可能性）への写像の合意。
3. 同一推論口（agent-model 記録再生）で両形式を生成できること（旧形式の生成役にも同じ隔離を適用）。

したがって P3 の基準比較は**構造比較まで**が結論。新方式側の基準測定（追加学習なし）は
P0d〜Wave C の agent-model 測定が既に担っており、旧方式の数字は作っていない。

## 2. gold・分割・版の追跡（確認結果）

| 対象 | 追跡の仕組み | 状態 |
| --- | --- | --- |
| ケースの分割 | `split`（dev/holdout）は schema で必須・欠落は loud に失敗。`group` は split を跨がない（loader とテストで強制） | 追跡できる |
| gold の根拠 | gold は `data/cases/*.json` の `expected` が正本（Git 管理下）。判断が割れるケースは `notes` に根拠を記録（Wave A）。export がケースファイル自体の SHA-256 を固定する | 追跡できる |
| run の版 | `inputs` に snapshot / contracts / fixtures の SHA-256、カタログ版、ケース ID 集合。config に session・条件・形式・prompt template 版・tokenizer provenance | 追跡できる |
| 契約版 | **欠落を発見**: P3 以前の run は契約版を config に記録しておらず、p0-1 の run（`3c149d0b`）と p0-2 の run が DB からは区別できない。P3 で `bench:format` の config に `contractVersion` を追加（新規 run から記録。既存 run の記録は書き換えない）。export は記録が無い run を `contractVersion: null` と正直に示す | 新規 run から追跡できる |

## 3. レビュー / export（新規）

- 実装: `bench/export/export.ts`（`buildRunExport` / `renderExportMarkdown`）+
  `bench/cli/export.ts`（`bun run bench:export -- --run <runId> [--db] [--out] [--cases]`）。
  テスト4件を `bench/export/export.test.ts` に追加。
- export の内容: run（kind・status・親 run・config digest）・config と inputs の verbatim・
  provenance（カタログ版・各 digest・契約版）・ケース一覧（split・group・期待種別・
  fixture 依存・gold の SHA-256）・セル別採点内訳（score 全体、criteria、check 指摘、
  model、出力 digest、トークン）・fixture 分離つき合計・修復の前後。合計は summary の
  写しではなく**作業DBの score 行から再計算**する。
- 照合: セッションの `summary.json` が同じ run のものなら、合計・全セルの状態/判定・
  修復の前後と合計を照合し、不一致は終了コード 1 で報告。summary が後続 run のものに
  なっている場合は superseded として扱い、その run のトークンは null（推定で埋めない）。
