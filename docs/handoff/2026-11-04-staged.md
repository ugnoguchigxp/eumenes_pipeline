# 段階生成＋カバレッジ見直し（staged）の実装と測定 — 長チェーンでは悪化し不採用

日付: 2026-11-04（日本時間）
証拠種別: agent-model（探索的）。生成は盲検の生成役サブエージェント＋記録再生、採点は決定的経路。
発端: chain-gekko-kamen（6タスク）で生成が3段に圧縮され、末端タスクが output.deliver の散文へ
吸収される「分解不足」を観測した（docs/handoff/2026-11-04-chain6.md）。利用者の決定:
「長いワークフローは一気にやらせず、段階的に生成し、合っているかの見直しを含める」。
文献調査（チェックリスト先行の二段生成＋カバレッジ検査を修復ラウンドへ）が後押しした方式を
bench 条件として実装し、baseline と比較した。

## 実装（bench のみ、src/・契約 p0-2 は不変更）

  chain-chair-compare / chain-garden-start、いずれも5〜6段・末端に文章作成と届ける/記録）。
  ケース総数 113→116（dev 73→76）。
- 作業2（commit `53e9048`）: 段階生成条件 `--staged`（既定 off、off では従来と完全同一）。
  - 段階A（列挙）: 依頼文だけから作業項目を列挙する短い生成を記録再生に載せた
    （`bench/format/enumerate.ts`、enum-v1）。項目 ID（w1, w2, ...）はモデルではなく
    bench が位置で決定的に付与する。列挙プロンプトにはカード・entry 名・gold を含めない。
  - 段階B（制作）: 項目リストを制作プロンプトへ渡し、各 step の task 冒頭に担当項目の
    印（[w1] 形式）を置かせる。印はカバレッジ計算の後、検証・採点の前に剥がす
    （bench 側の補助チャネル。定義の構造・契約は変えない）。
  - 段階C（見直し）: `--coverage-repair`。項目 ID と step が引いた ID の決定的な集合差分を
    取り、未カバー項目を機械エラー（場所=項目 ID、内容=項目文）として既存の修復ループへ
    1回渡す（手順の挿入を許可）。gold は渡さない。機械的失敗セルは対象外。

## 何が起きたか

1. **動機づけの失敗（分解不足）は baseline では再現しなかった。** baseline は長チェーンを
   c1 で4/4、c2 で3/4 合格し、pipeline と答えた長チェーン7セル全てで gold entry を
   完全被覆・段数も想定どおりだった。c2 の2件の不合格（chain-festival-guide /
   chain-trip-prep）は分解不足ではなく needs_input への反転（情報不足判定の揺れ、
   従来から知られたクラス）。chain6 の3段圧縮は n=1 の観測であり、コホートが変わると
   出なかった。発端の失敗様式そのものが生成コホート依存だった可能性が高い。
2. **staged は項目被覆を100%にしながら長チェーンを壊した。** 26セル全てで印は全項目に
   引かれ、段数も想定どおり（過剰分解なし、短チェーンは18/18で悪化なし）。しかし
   長チェーン8セル中7セルで、「文章を書く」項目の担当 entry が gold の `docling.desk`
   から `dots.delegate` へ系統的に置き換わった（c1: 4/4件、c2: 3/4件。文章作成を
   「コンテンツ作業を任せる」入口へ割り当てる読み）。被覆は「項目がどこかの step に
   紐づく」ことしか見ておらず、**entry 選択の誤りは被覆を満たしたまま通過する**。
3. **段階Cは26セル中0セルで発動した。** 未カバー項目が皆無だったため修復 request は
   両コホートとも0件で、staged+review は staged と完全同一の結果になった。印の引用は
   安く満たせる規律であり、カバレッジ信号（印の集合差分）は今回の実際の失敗
   （entry の置き換え）を原理的に検出できない。段階Cの寄与は分離した結果「ゼロ」。
4. 短チェーンでは staged の悪化は無かった（18/18、段数差±0）。悪化は長チェーンの
   文章作成項目に集中した。

## 判定: 不採用

- 採用条件（長チェーンで passed またはカバレッジが明確に改善し、短チェーンで悪化なし）に
  対し、長チェーン passed は 7/8 → 1/8 と明確に悪化した。コホート揺れの範囲ではない
  （両コホートで同じ置き換えが再現）。コストは生成+1段・トークン約+10〜12%。
- 実装は bench の実験条件として残置する（既定 off、accuracy-2 の不採用条件と同じ扱い）。
  本番の制作経路（baseline＋ID正規化＋修復ループ）は不変更。

## 項目 ID 結び付けを本番契約へ上げるべきか — 所見: 上げるべきでない

- 今回の証拠では、項目 ID の結び付けは「被覆の見かけ」を作るだけで、品質の実体
  （正しい entry への割り当て）を保証しなかった。契約化すると、この弱い信号が
  ホスト側の合否判定に混ざり、「印が揃っているから完全」という誤った安心を生む。
- 検出すべきだったのは entry 選択の誤りであり、これは項目→entry の意味対応の検査を
  意味し、gold なしでは決定的に検査できない領域（判定はLLM・検査はコードの原則とも
  衝突する）。再挑戦するなら、列挙項目に「成果物の種類」程度の型を付け、カード側の
  出力種別と突き合わせるような、より意味に近い補助チャネルが要る。それでも bench 側で
  効果を実測してから契約化を論じるべきで、現時点では bench の補助チャネルに閉じる
  判断（今回の設計どおり）が妥当。

## 留保

- 証拠は agent-model（Muse 自身が生成役）。Luna・Haiku 級での挙動は未測定で、
  特に dots.delegate への置き換えが対象モデルでも起きるかは分からない。
- コホートは2つだけ。baseline 側も c1（全合格）と c2（needs_input 反転2件）で揺れており、
  小さい差は判定に使っていない。長チェーンの悪化は両コホート同型の再現があるため
  揺れとはみなさない。
- docling.desk のカード自体が「文書画面の準備」という狭い目的を掲げており、文章作成の
  正解 entry とする gold の慣行との間に元々緊張がある。staged の置き換えはこの曖昧さを
  増幅した面があり、カード文面の側の問題として別途切り分けが可能（今回の範囲外）。
