## 追加したケース（data/cases/chain-gekko-kamen.json、dev、usesFixtureContracts=true）

想定する6段と gold の表し方。ケース形式の gold は entry 集合（requiredBundles）と
材料の配線（requiredMaterials）でしか表せないため、段の内訳と根拠はケースの notes にも記した。

| 段 | entry | 役割 | from（想定） |
| --- | --- | --- | --- |
| 1 | web.search | 月光仮面の素性を確認 | request |
| 2 | web.search | 主題歌・時代背景の追加確認 | request |
| 3 | image.create | 調査を材料にイメージ画を生成 | 1（+2） |
| 4 | music.create | 主題歌・時代背景を材料に60年代の曲調のイメージソング | 2（+1） |
| 5 | docling.desk | 調査を材料に簡単な紹介文章を作成 | 1, 2 |
| 6 | dots.delegate | 画像・音楽・紹介文を受けて利用者へ届ける | 3, 4, 5 |

- requiredBundles: web.search / image.create / music.create / docling.desk / dots.delegate（5 entry。
  web.search が2段あることは集合では数えられない — 下記「gold の表現力」を参照）。
- requiredMaterials: web.search（調査結果が後段へ渡る）、image.create・music.create・docling.desk
  （3成果物が全て届ける段か output へ渡る）。
- finalArtifact: schema 上1つだけ名指し可能なため画像（image）を代表にした。音楽は
  requiredBundles と requiredMaterials で必須化してある（edo-research-image-music の前例と同じ扱い）。
- usesFixtureContracts=true の根拠: web.search は旧形式（unbound）、image.create と music.create の
  出力は fixture 契約。loader テストの再計算とも一致。
- 件数の追随: ケース総数 112→113（dev 72→73）のため、固定していたテスト2件
  （bench/cases/cases.test.ts、bench/selection/experiment.test.ts の dev 件数・評価対象 60→61）を
  更新した。過去の測定 run は入力にケース集合を固定しているため影響なし。

## 結論: 今回は正解に導けなかった

- 機械的な失敗（ID 様式）は従来どおり正規化段で完全に吸収できた。残った失敗は意味側のみで、
  しかも needs_input 閾値のような判断の揺れではなく、**作業分解の不足（under-decomposition）**である。
- 6タスクのうち手順になったのは3つ。手順にならなかったのは:
  - 紹介文章の作成（docling.desk）: output.deliver の散文（「検索結果をもとに簡単な紹介文章を作成し、
    …紹介する」）に吸収された。手順として存在しないため、実行も検証もされない。
  - 届ける段（dots.delegate）: 同じく output の散文に吸収された。
  - 2件目の web.search（主題歌・時代背景）: 1件目の調査に統合された（entry 集合の gold では
    そもそも検出できない。music.create の task が「確認した月光仮面をもとに」とだけ書き、
    主題歌の調査を材料として要求していない点に痕跡が残る）。
- 長いチェーン特有の問題として当初想定した「from 参照の破綻・段の重複」は**観測されなかった**。
  実在する段同士の配線は正確だった。観測された固有の失敗様式は参照の破綻ではなく、
  **末端寄りのタスク（文章作成・受け渡し）が output の散文へ吸収され、手順の数が依頼のタスク数より
  少なくなる**ことである。チェーンが長くなるほど「全部やったつもり」の散文に吸収されるタスクが
  増える危険がある。

## gold の表現力についての注記

- 現行の gold は entry の集合と材料配線しか表せないため、「web.search を2段使う」こと自体は
  採点対象にできない。本ケースでは段の内訳を notes に明記し、調査→生成→作成→受け渡しの
  配線は requiredMaterials で強制した。段数そのものを gold 化したくなったら、ケース形式の
  拡張（最低段数や entry の多重度）が別途必要になる。
