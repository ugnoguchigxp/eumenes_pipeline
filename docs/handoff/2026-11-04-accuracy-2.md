# Handoff: 精度向上策 項目2 — needs_input 閾値の安定化

- 日付: 2026-11-04
- 証拠種別: **agent-model（探索的）**。受入基準は利用者決定で Luna/Haiku 級だが、この環境での測定は agent-model で行った。
- 結論: **(A) 指示文規約・(B) triage 先行分離のいずれも不採用**（反転は減らず、採用基準「反転が明確に減り passed が悪化しない」を満たさない）。実装は compact / oneshot と同じく条件レジストリに実験として残す。

## 実施したもの

- (A) 指示条件 `threshold`（`--condition threshold`）: 共通指示へ判断規約 threshold-v1 を追加。規約は一般原則のみ（対象が特定できなければ needs_input、手順・体裁・成果物の指定不足は進める、添付素材と「現在の〜」等の文脈参照は対象を特定する）。具体ケースの答を含まないことをテストで固定（ケース ID・entry 形式文字列の不在を検査）。
- (B) triage 先行分離（`--triage`）: compose の前に、依頼文＋素材だけ（カードなし）で「進める / 不足を質問」の判定だけを行う短い生成（tr）を挟み、結論を compose プロンプトの参考節（機械的強制ではない）として渡す。判定不能なケースは compose が欠落として数えられる（黙って進めない）。

## 測定条件

- fresh dev 60 件（compose セット）、形式 json、全カード、修復なし、条件ごとに 2 コホート（同一条件の反復生成で反転を測る）。生成は盲検の生成役＋記録再生、採点は決定的経路。
- この生成バッチは step ID の snake_case がほぼ全域に現れたため、素の passed は全条件 9/60 に潰れ比較不能。**passed の比較は正規化段（項目1、採用済み）適用後に統一**した。kind 判定（needs_input か否か）は ID と無関係のため素の出力で測る。

| 条件 | gold 一致（c1 / c2） | 反転（部分集合） | 反転（全 60 件の kind） |

| baseline | 12/17, 13/17 | 1（compute-to-diagram） | 1 |

- 過去の反転ケースへの効果: compute-to-diagram は (A) では両コホート needs_input に倒れ（gold=pipeline、悪化）、(B) でも反転継続。weather-then-timer-early は全条件で両コホート needs_input（gold=pipeline）— 規約でも triage でも動かなかった。
- (B) の良い観測: browser-fill-form・chain-hiking-plan は baseline で両コホート needs_input だったのが、triage では両コホート pipeline に安定（gold 一致）。ただし compute-to-diagram / kanban-from-weather の反転が残り、純増減では baseline と同等以下。
- triage 自体の判定: c1 proceed 51 / needs_input 9、c2 proceed 49 / needs_input 11、欠落・不正 0。コストは 60 件で prompt 13,841 + output 約 670 トークン（1 件あたり約 240）。

## 判定

- (A) 不採用: 反転は増え（3 vs 1）、passed も微減。規約の明示は今回の書き方では効かなかった。
- (B) 不採用: 一致率の平均は最良（14.0 vs 12.5）で passed 平均も +0.5 だが、**反転の削減という主目的が達成できていない**（2 vs 1）。差は揺れの範囲であり、採用基準に届かない。再測するなら triage 結論を「参考」ではなくより強い形で渡す変種が候補だが、本ラウンドでは追わない。
- 測定の衛生メモ: 同一条件・同一プロンプトの反復では kind 反転は 60 件中 1〜3 件に留まった。Wave C で観測した ±5 件級の揺れは、条件・バッチ差を含むものだった可能性が高い。今後の反転比較は同一条件の反復を基準にする。
