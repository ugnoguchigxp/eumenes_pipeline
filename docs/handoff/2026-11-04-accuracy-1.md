# 精度向上策 1: step ID の決定的正規化段

日付: 2026-11-04（日本時間）
証拠種別: agent-model（探索的）。受入基準は利用者決定で Luna/Haiku 級だが、本測定は従来どおり agent-model の記録再生で行った。
判定規律: 実装＋検証し、改善したら採用、効果が下がったら不採用。差がコホート揺れの範囲なら改善と呼ばない。

## 施策

最大の機械的失敗クラス（step ID の様式違反。holdout 失敗 9/40 件、修復ループでも 25 件中 1 件残存）を、モデルの再生成（修復ループ）に頼らず決定的に処理する段を追加した。

- 実装: `bench/formats/normalize-ids.ts` の `validateAuthoring` が authoring ゲート（`AuthoringOutcome` 検証）を担い、正規化は「parse 済み ready が ID 様式（`definition.steps.*.id` のパターン）だけを理由に落ちた場合」に限り発動する。
  - 書き換え: パターンを満たす ID は不変。違反 ID のみ `normalizeStepId`（小文字化、非 `[a-z0-9]` の連続を単一ハイフンへ、先頭は英字を保証、40 字に切り詰め）で正規形へ。参照（`steps[].from`、`output.from`）は写像に従って付け替える。ID 以外の内容は一切変えない（構造化クローンへの写像適用のみ）。
  - 安全規律: 最終 ID 集合に対する単射性を必須とする。正規化後に衝突する場合、および書き換えた ID が予約参照 `request` に一致する場合は、正規化を拒否し元の不合格（エラー文面も不変）を残す。拒否されたセルは従来どおり修復ループの対象になりうる。
  - 配線: `bench:format --normalize-ids`（既定 off、off では従来と完全同一）。run config に `normalizeIds` / `normalizeVersion: step-id-normalize-v1` を記録。セル・修復試行に `idsNormalized` フラグ、score criterion `ids_normalized`、集計 `normalize {attempted, recovered}` を summary と export の両方で追跡可能にした（構文復元段の流儀と同じ）。export の保存形定義は同じゲートで再導出する。recordings は一切書き換えない。
- `src/`・契約 p0-2 は不変更。

## 検証

### 単位・配線テスト

- `bench/formats/normalize-ids.test.ts`（12 件）: snake_case→正規形と参照追随、衝突時の却下、`request` への着地の却下、正常 ID への不発動、ID 以外の理由を含む失敗への不発動、元の値が破壊されないこと。
- `bench/format/run.test.ts`: フラグなしでは不合格のまま・ありでは回復して passed、拒否ケース（`Request`→`request`）は attempted 1 / recovered 0、recording バイト不変、summary 形状。
- `bench/export/export.test.ts`: フラグ・保存形定義（書き換え後の ID）・`normalizeEqual: true`。
- ゲート: `bun run check:all` 306 tests / 0 fail（従来 292、+14）、`bun run bench:verify --db :memory:` 87/87。

### 実データ再評価（Before/After）

既存セッションの recordings を正規化 on（修復なし）で再評価した。比較対象は修復ループ込みの到達点。

| セッション | 素の compose passed | 正規化のみ passed | 修復込み passed（参照） | 正規化 attempted → recovered | 不要になる修復トークン |
| --- | ---: | ---: | ---: | ---: | ---: |
| dev-subset-1（60件） | 42/60 | **51/60** | 51/60 | 9 → 9 | 29,154 |
| dev-compact-1（60件） | 48/60 | **52/60** | 52/60 | 4 → 4 | 12,603 |
| dev-minjson-1（60件） | 50/60 | **53/60** | 53/60 | 3 → 3 | 17,450 |
| holdout-baseline-1（40件） | 27/40 | **35/40** | 35/40 | 9 → 9 | 54,311 |
| 合計 | | | | 25 → 25 | **113,518** |

- 正規化のみで、全セッションとも修復込みの到達点に完全一致した。修復ループが回復していた 25 件すべてが機械的に回復した。
- holdout の残存失敗 docling-open は、正規化でゲートは回復したが意味側（bundles）の不一致で不合格のまま残った。これは修復ループでも回復しなかった 1 件と同一で、正規化が意味判断に踏み込んでいないことの確認にもなった。
- 冪等性: ID 失敗のない dev-baseline-1（180 セル・3 形式）を正規化 on で再走し、passed 170/180・parse 180/180・check 144/144 と記録済み数字に完全一致（attempted 0）。
- export の再計算でも holdout 正規化 run（`a822db80`）の normalize {9, 9} と passed 35/40 が一致。
- 注記: dev-subset-1 の初回再評価でケース集合を取り違えた run（`c30d7df6`、compose dev-60 で実行し ni/us 9 件が missing）が作業 DB に残っている。追記専用のため削除せず、ここに記録する。比較には正しいケース集合（選定 dev-60）の run `6bd90315` を使った。
- 各再評価後、セッションの summary.json は元の run のものへ復帰済み（subset `22a6ab8f`、compact `d1f33d6d`、minjson `6b9c91f0`、holdout `75a5831c`、baseline `766c7dc2`）。

## 判定: 採用

- 機械的回復が修復ループと同等（到達点が全セッション一致）で、副作用なし（冪等性・拒否規律・テストで固定）。修復呼び出し自体が不要になるため、推奨構成（JSON＋全カード＋minified 生成＋pretty 保存）において、正規化段は修復ループの前段として組み込む。
- 既定 on 化はしない（本書の判定規律どおり、既定変更は提案に留める）: ホスト統合時および bench の推奨実行では `--normalize-ids` を付けることを提案する。修復ループは、正規化で回復しない機械的失敗（parse 崩れ・check エラー等）のために残す。
- 留保: 本測定は agent-model の既存 recordings に対する再評価であり、新規生成での効果（生成側が ID を直す方向に変わるか等）は測っていない。対象モデルでの命中率は未測定（構文復元段と同じ留保）。
