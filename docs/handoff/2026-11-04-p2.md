### 2. 薄いホスト adapter（Eumenes 側ブランチ）

配置: `vendor/pipeline/`（tarball・`.sha256`・`manifest.json`）＋ `package.json` の依存
`file:vendor/pipeline/eumenes-pipeline-0.0.0-ce4682a6b74f.tgz`（bun.lock の差分は3行のみ）。
adapter 本体は `api/application/pipelines/pipeline-host-adapter.ts`（composition 層の既存慣行に合わせた）。
adapter は `PipelineHost` を、子実行を1件実行する関数（`ChildExecutor`）の上に実装する。
DB トランザクションを伴う実 dispatch（`prepare`/`execute`/`adoptInTransaction`）への結線は
本体統合時（承認後）の作業で、本検証の範囲外（下記「未検証」）。

#### 写像: StepExecution → ChildExecution

agent-runtime の launch（`execution-store`）が組み立てる項目集合と一致させた。

| ChildExecution | 由来 |
| --- | --- |
| `chainRevisionId` | host が起動時に再解決（`stepToolchainInTransaction` 相当のコールバック）。計画が固定した `revisionId` より再解決の結果が勝つ（現行 pipeline 手順と同じ規則）。解決できなければ手順は `failed` + `pipeline_toolchain_unavailable`（runtime の停止コード）で返り、子は作られない |
| `request` / `arguments` / `refs` | step の `request` / `arguments` / `references`。参照は host 自身の `executionReference` schema で検証してから渡す（上限超過は切り捨てず loud に失敗） |
| `source` | `{ conversationId, messageId }` は host context、`runId` は step の `runId`、`request`/`digest` は step の `source` |
| `deadline` | `min(step.deadline, 親期限 − 45s, binding 独自期限)`（launch の規則どおり） |
| `modelCalls` | host context の割当て（runtime の上限12・予算配分の考え方） |
| `id` / `executionId` / `revision` / `step` | host が発行: 子 id、親実行 id、親の要求 revision、連番の ordinal（context の基点から） |

#### 写像: ChildResult → StepResult

| StepResult | 由来 |
| --- | --- |
| `state` | そのまま（8状態の union が両契約で同一） |
| `summary` / `output` / `code` / `question` / `references` / `links` / `modelCalls` | そのまま（参照は項目ごと写す） |
| （落とす）`ref`・`questionSchema`・`questionDeadline` | host 内部の prepared ref と質問の詳細。package 契約は質問文のみを持つため adapter 境界で落とす。本体側で必要な場合は host 内に留まる |

#### 確認項目（adapter の単体試験11件、全て通過）

| 確認項目 | 結果 | 試験 |
| --- | --- | --- |
| (a) 実行計画が既存の子実行へ写る | 可 | 2手順の計画→子2件が順序・ordinal・source・期限・割当てどおりに組み上がり、手順2が手順1の host 発行参照（全項目一致）を受け取る。成果物は最終手順の参照 |
| (a') 起動時再解決と binding 期限の優先 | 可 | 再解決の版が計画固定の版に勝ち、binding 期限が両者に勝つ |
| (a'') 実行不可の入口は停止コードで止まる | 可 | 子を作らず run が `pipeline_toolchain_unavailable` で停止し、成果物は null |
| (b) 取消後の結果を採用しない | 可 | 取消後に `completed` で確定した結果は `after_cancel` として不採用。構造だけの `{aborted}` 信号も executor の `AbortSignal` へ橋渡しされることを別途確認 |
| (b') 期限後の結果を採用しない | 可 | 期限後に届いた `completed` は `after_deadline` として不採用、後続手順は実行されない |
| (c) 一部成功を全成功としない | 可 | 手順2の失敗で run は停止（状態 `stopped`、成果物 null、手順3は未実行）。`waiting_input` は質問を表に出して停止し、成功にならない |

試験の駆動ループは bench driver と同じ採用規律（順序、`from` の参照だけ、最初の未採用で停止）を
踏んだテスト用足場であり、製品コードではない。bench driver との意図的な差分は1つ:
完了 output の schema 照合を含まない。根拠は P0a の確定事項（command binding の宣言 schema は
受領票であり完了 output の schema ではない。本体でも `stepFault` の判定は状態＋必須パスの有無）。

## 巻き戻し手順（Eumenes 側）

検証ブランチ上の1 commit（`9101985`）に全変更が閉じている。

1. `cd ~/workspace/dev/eumenes && git checkout main`（main は無変更）。

3. `node_modules/eumenes-pipeline` が残る場合は `bun install --ignore-scripts --frozen-lockfile`

削除すれば足りる。本体サーバーの起動・停止は本作業では行っていない。
