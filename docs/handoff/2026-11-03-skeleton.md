### 独立レビューと修正

構築後に独立したレビューを1回行い、指摘12件をすべて修正した（通過済みのテストでは見つからなかったもの）。

- 作業DB: `INSERT OR REPLACE` で終了済みの行を上書きできた → `recursive_triggers` を有効にし、終了済みのrun・試行への追加もトリガーで拒否。空でない既存DBを渡されたら初期化を拒否。
- 到達ガード: `Bun.$`・`Bun.sql`/`redis`/`S3Client`・`Worker`・DNS・`tls`/`dgram`/`http2` を実行時に遮断。`Bun.fetch` は書き換え不能なため、静的検査で使用を禁止（`require`・`getBuiltinModule`・`"bun"` からの値import・`Bun[...]` も禁止）。**限界**: 名前付きimportと `Bun.fetch` は実行時には塞げず、静的検査だけが守る。
- `bench:verify`: 到達件数を途中で捨てていた → 開始時点からの差分で判定。例外時にrunが `completed` になっていた → `failed` を記録。
- `src/` の純度: 型検査で配布ビルド設定（`types: []`）も検査。
- 梱包: 成果物ごとのディレクトリ、排他的作成、tarball実体の中身検査、git不明時の `dirty: null`。
- モック: 抽出済み契約がない引数も、カードのschemaで必ず検証。
- Museアダプター: 不正なJSON行で落ちない、使用量がなければ呼出し回数も `null`、タイムアウト後の強制終了、一時ディレクトリがリポジトリ内なら実行を拒否。
- スナップショット: パスをURIエンコードして開く。抽出スクリプトもmanifestのdigestを照合。

## 4. 設計の判断と理由

1. **1手順 ＝ 登録済みtoolchain入口の子実行1回。** Eumenes の `ChildExecution` → `ChildResult` に対応させた（`src/contracts/execution.ts`）。既存パイプラインの `toolchainStep` も `toolchain`・`request`・`uses` で子実行を起動しており、新定義の `bundle`/`entry`・`task`・`from` とほぼ1対1で対応する。
2. **部品の識別は入口（toolchain ID）、bundle は属性。** データ上、1つのbundleに複数の入口がある（`browser.capture` の bundle に `browser.capture`・`browser.operate`、`terminals-screen` に `claude-code.repair`・`.request`）。定義の `bundle` には入口IDか、入口が1つだけのbundle IDを書ける。複数あるのに `entry` がなければ `ambiguous_entry` で止める（暗黙の既定入口を作らない）。どちらの書き方を採るかは P0b の比較事項のまま。
3. **結果は丸ごと参照で渡す。** `from` は依頼または前の手順の結果全体を指し、ホストは `ExecutionReference` 相当の参照を渡す。式は埋め込めない（strict schema）。
4. **後続へ渡すのは、完了し、宣言した出力契約に適合した結果だけ。** 失敗・取消・期限切れ・入力待ち・不確定はそこで止める。取消後・期限後に届いた結果は採用しない（`bench/mock/driver.ts`）。Eumenes側の実行器も同じ規則を守る必要がある。
5. **対応度は3段階。** `ready`（カタログ・Eumenesコード由来の入出力契約）、`partial`（fixture出力、または要約のみ）、`excluded`。判定は実行種別・binding・adapter・schema参照の事実だけで行い、題名や説明文は読まない。理由はすべて `reasons` に残す。
6. **instant の型付き引数は未決。** モックは2つの方針を持つ。`entry-structures`（部品自身のLLMが依頼から構造化する。モックは合成し、そのことを記録）と `required`（手順が渡す。なければ `missing_arguments`）。plan §5 の「最小の入力対応指定」を採るかは P0b で決める。
7. **モックは正解を知らない。** 選ばれた部品の契約どおりの合成値を返し、誤選択にはその誤った部品の結果を返す。自分の契約に合わない値を作ったら `MockDefect` を投げて止める（ツールの結果として返さない）。
8. **作業用SQLiteは追記専用。** 終わったrun・試行の更新と、すべての削除をトリガーで拒否する。条件を変えたら新しいrun。
9. **推論はMuse。** 毎回リポジトリ外の空の一時ディレクトリで `muse exec --preset empty` を実行し、リマインダー・Web・利用者への質問・個人ルールを無効化する。このリポジトリのAGENTS.mdやケースがモデル側へ渡らない。exec に system プロンプトの指定がないため、system はプロンプトの先頭に区切り付きで連結している（形式比較では両条件で同じ連結を使うこと）。
10. **データはリポジトリで管理。** 利用者の合意（2026-11-03）により、スナップショットSQLite・抽出した契約・生成した棚卸しはGitで管理する。作業用DBと `data/runs/` は管理外。配布tarballには含めない（梱包スクリプトが検査する）。

## 5. Eumenesへの取込みの対応

| Pipeline | Eumenes |
| --- | --- |
| `PlannedStep { entry, task, from }` | `pipelineDefinitionV1` の `toolchainStep { toolchain, request, uses }`（変換方式の場合） |
| `PipelineHost.executeStep(StepExecution)` | agent-runtime の子実行（`ChildExecution`: request・refs・source・deadline） |
| `StepResult` | `ChildResult`（state・summary・output・references・links・modelCalls） |
| `StepReference` | `ExecutionReference` |
| `ComponentRecord` | 有効なtoolchain revision・binding・`hostAdapterDescriptions`・schema provider から組み立てる |
| `InferencePort` | 保存済みのLARM接続（モデル名をコードに固定しない） |
| `CancelSignal` | `AbortSignal`（そのまま渡せる構造型） |

P0e で比較する2案: (a) 既存の `pipelineDefinitionV1`（2〜8手順、title・useWhen等が必須）へ変換する、(b) 子実行を直接呼ぶ薄いhost adapterを作る。どちらでも、ドライバーの規則（§4の4）を Eumenes 側で保証する必要がある。

## 7. Ruri（文脈判定reranker）の再学習との関係

2026-11-03、利用者の環境で Ruri を依頼・参照構造データで再学習した（別作業。報告は利用者から受領）。新network `ruri-conv20-structure-v1-s0-fp32-v1`、元モデル `cl-nagoya/ruri-v3-reranker-310m`（revision `bb46934e…`）、seed 0・FP32の1本。復元後の `model.safetensors` の SHA-256 は `167add95…691732`。**Providerへの配備は同日、利用者が進行中**で、報告時点の稼働networkは旧 `ruri-conv20-s0-fp32-v1`。

この bench への影響:

- **Providerに触れない。** 起動・停止・再起動・設定変更・学習の有効化をしない。配備の状態は利用者に確認する。
- **network を記録する。** Router の best-v2 や reranker の点数を使う測定では、run の config に network名・モデルhash・取得時刻を記録し、旧network・新networkの結果を同じ表で混ぜない。配備の切替えをまたいだ run は別条件とする。
- **学習文との重なりを確認する。** 新モデルは追加63文（正解は `image.create` 20・`music.create` 16・`ui.compose` 8・`model3d.studio` 7・`excalidraw.edit` 4・`conversation.respond` 8）と既存811組で学習した。評価ケース（`data/cases/`）がこれらと重なると、Router経路の成績が水増しされる。学習データの本文はこのリポジトリにないので、照合できるまで Router 経路の成績を「未見データでの精度」と呼ばない（plan §9）。
- **既知の弱点。** 学習文の確認でも、`conversation.respond` を正解とする8文は旧・新とも 0/8 で最上位にならなかった。「部品を使わず会話で答えるべき依頼」や「対応できない依頼」の判定を、Router の上位候補に頼る設計にはしない。新モデルでは学習内容（会話を正例として学習した）が旧と違うので、network別の説明が必要になる。
- **reranker・embedding の接続口は未実装。** 追加するときは `src/ports.ts` と同じ型付きの接続口にし、到達ガードで許可するのはその接続先だけにする（現在のガードは `fetch` を全面的に塞いでいる）。query の埋め込みや reranker の点数が得られない経路は「未測定」とする（plan §10）。
