# P4 引き継ぎ（2026-11-04）— 学習相当の調整と holdout 検証

P4（plan §10）の実施記録。原則は事前に固定した: **調整は dev だけで行い、凍結した構成を holdout で1回だけ評価する。holdout の数字を見てから構成は変えない。改善しない場合は現行方式を維持する。**

対象は2つ。(1) 部品選択（検索）のパラメータ調整と holdout 選択評価、(2) holdout 全件での制作（compose）の未見通し確認。基盤モデルの追加学習はこの環境では実施条件が無く、実施条件のみを記録する（§5）。

証拠の種別: 埋め込みは bench ローカルの e5 Provider（network `local-e5-small-qint8`、intfloat/multilingual-e5-small の ONNX QInt8、space digest `dd476dd0…`、384次元）。制作は agent-model（Muse 自身の推論を盲検の子エージェントで生成し記録・再生）。いずれも弱い対象モデル（LFM2.5）での正式受入ではない。本番の Ruri Provider には触れていない（bench ローカル provider が落ちていたため `E5_PROVIDER_PORT=8377` で再起動したのみ）。

実装: `bench/selection/tuning.ts`（構成の定義・融合・凍結規則）、`bench/cli/selection-tuning.ts`（CLI `bench:selection-tuning`。holdout は `--configs` 指定なしでは実行を拒否し、掃引できない作りにした）、`bench/selection/tuning.test.ts`（10件）。`src/` の公開API・契約 p0-2 に変更なし。

### 失敗の切り分け（13件）

**機械的失敗 9件**（すべてステップIDの snake_case が `/^[a-z][a-z0-9-]{0,39}$/` に違反した authoring 失敗。内容の criteria は docling-open を除き全て true）:

dev の各コホート（subset / compact / minjson）でも同じステップID クラスが繰り返し現れており、コホート固有ではなく生成側の安定した癖であることが holdout でも再確認された。

## 5. 基盤モデルの追加学習 — 実施条件（未実施）

この環境には LFM2.5 の学習用 GPU・学習エンドポイントが無いため実施しなかった。以下が揃えば実施できる、という条件を記録する。

- **必要なもの**: 対象モデル（LiquidAI/LFM2.5-24B-A2B）を学習可能な形で扱える環境 — 24B MoE の LoRA ないし全パラメータ学習が回る GPU ノード、または同等の学習エンドポイントへのアクセス。推論専用の到達可能性（現状の agent-model 対照や埋め込み provider）では代替できない。
- **学習対象の候補**: (a) 制作生成そのもの — dev split から作る「依頼→定義」ペアでの微調整。特に今回の holdout で支配的だったステップID の様式規律と、`needs_input` 判定の閾値の較正が第一候補。(b) 修復行動 — 機械的エラーのフィードバックから最小修正で直す振る舞い（ただし修復ループは現行でも bench で 13/13 + 8/9 と効いており、モデル側に埋める優先度は低い）。(c) 検索側の適応は基盤モデルではなく埋め込み/reranker 側の話であり、ここには含めない（本番の再学習済み Ruri は利用者配備物で対象外）。
- **比較の方法**: 学習データは dev 由来のみから作り、holdout を学習入力に混ぜない。評価は今回と同一の凍結ケース・split・採点器・条件で行い、dev で調整→holdout で1回だけ評価の手順を踏む。改善と退行を同一条件の表で示し、改善が無ければ現行方式を維持する。agent-model の数字を対象モデルの受入に流用しない。
