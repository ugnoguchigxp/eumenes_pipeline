# Handoff: 精度向上策 項目4 — 警告駆動の自己レビュー

- 日付: 2026-11-04
- 結論: **不採用（未測定・対象不足）**。実装は行わない。理由は対象セルの実数調査（census）の結果であり、ブリーフが認めた打ち切り条件に該当する。

## 予定していた施策

compose が check を通ったが warnings（severity=warning の機械診断）を持つセルに限り、機械的な指摘だけをフィードバックして 1 回見直させる段を、修復ループの枠組みで追加する（フラグ既定 off、gold は渡さない）。passed の変化と state / bundles / materials のドリフトで判定する予定だった。

## census（記録済み全 run の checks テーブル集計、決定的・再現可能）

警告は work DB の `checks` テーブルに severity 付きで記録されている。全記録の集計:

| 対象 | 警告セル（distinct trial） | 内訳 |
| --- | ---: | --- |
| 全 compose trial 3,906 件中、警告あり | 31 | 全て `unused_result` |
| `arguments_unchecked` | **0**（全期間・全 severity で未発火） | — |
| dev-baseline-1（180 セル、3 形式） | 6 trial / 9 行 | **全て free-md 形式。JSON セルは 0** |
| acc2 fresh dev-60・JSON（6 セッション × 60 = 360 セル、正規化適用後の到達分） | **同一 1 ケースのみ** | 下記 |

- acc2 の 6 セッション中 5 セッションで警告を出したのは **chain-hiking-plan の 1 セルだけ**（`unused_result`、steps.2 の set-timer の結果が未使用）。しかもその全てが **既に passed** していた。
- 警告を持ちながら passed でなかったセルは、全記録で chain-meeting-prep（free-md）の 1 trial のみ。

## 判定理由

- 推奨構成（JSON）での対象母数は **60 件あたり約 1 セル（1.7%）** で、しかも恒常的に同一ケース・同一指摘・既合格。この母数では fresh 測定を組んでも、改善の上限は +0（対象セルは既に合格しており passed は上がりようがない）で、観測できるのはドリフト（悪化）リスクだけになる。Before/After の物差しが成立しない。
- もう一つの想定警告 `arguments_unchecked` は記録上未発火であり、レビューの入力自体が存在しない。
- よって「対象セルが少なすぎて測れない場合は実数を報告して不採用（未測定）としてよい」というブリーフの打ち切り条件を適用する。修復ループ枠組みへの実装も、測定できない変更を本流へ入れる理由がないため行わない。

## 再開条件（将来の自分への申し送り）

以下のいずれかが起きたら再測の価値が出る:

- 対象モデル（Luna/Haiku 級・Ornith 等）での実測で、合格セルの 5〜10% 以上が警告を持つようになった場合。
- `arguments_unchecked` が実際に発火し始めた場合（引数の未検証は unused_result より実害が大きい）。
- 警告を持つ「check は通るが passed でない」セルが複数ケースで観測された場合（現状 1 件のみ・非推奨形式）。
