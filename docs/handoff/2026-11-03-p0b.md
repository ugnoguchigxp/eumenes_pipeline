# P0b 比較用契約の固定と、P0a の確定（2026-11-03）

実施: Muse。前提は引き継ぎ（2026-11-03-skeleton）§8 のうち、旧形式9件は (B)（bench の fixture 契約で補い、実カタログ由来と分けて報告）、fixture 契約は現行のまま。推論の担当は利用者の指示（2026-11-03）により `muse` CLI ではなく Muse 自身（agent-model 方式。生成役には正解を見せず、出力は記録して再生する）。P0d の結果は agent-model の証拠として区別し、実モデルの受入とは呼ばない。

## 1. P0a の確定事項: `ChildResult.output` の実際

Eumenes 本体（`~/workspace/dev/eumenes`、HEAD `98b188d` = 契約抽出の出所 commit）を読み取り専用で確認した。

- 契約型の `ChildResult.output` は無型（`unknown`）で、契約自体は何も保証しない。
- command 型・ジョブ型 adapter（compute、shell/cli、browser.capture、kanban、model3d、terminals 等）: 完了時の output はドメインの作業結果レコード。受付時の受領票（`{action, jobId}`）とは別物で、その schema はカタログに存在しない。
- command 型・同期 bound adapter: output は `answerContext ?? receipt`。受領票が output に入るのはこの経路だけ。
- browser.operate の effect 経路: 完了時に output を付けない。
- instant 型: output は設定されず、回答は summary に入る。
- summary は経路依存（instant = 回答文、ジョブ型 = `JSON.stringify(output)` の先頭2000字、同期 bound = receipt 等の JSON 文字列）。
- references は adapter がほぼ常に空を返し、実体は実行ストアが結果採用時に付ける host 発行の「子実行の確定結果」への参照。

含意: カタログの binding 出力 schema（例: `domain:compute.receipt@1`）は受付 receipt の宣言であり、完了時に後続へ渡る output の schema ではない。棚卸しの「ready 部品の出力契約 = 受領票」という読みは、完了結果の受け渡しについては成り立たない。`src/contracts/component.ts` の `ComponentCard.output` と `src/check.ts` の `PlannedStep.output` のコメントに、この区別を明記した。個別 adapter のうち dots.delegate、docling.desk、timers.manage がどちらの経路かは個別未確認（timers は同期 bound 側が濃厚という以上は断定しない）。

## 2. P0b で固定した契約

| 項目 | 決定 |
| --- | --- |
| 入口の指定 | 部品カードは公開入口ごとに作る。定義の `bundle` には入口 ID、または bundle ID + `entry` を書ける。複数入口の bundle で `entry` を省くと `ambiguous_entry` で止める（暗黙の既定入口は作らない）。この方式を比較の前提として固定する |
| instant の型付き引数 | 手順に任意項目 `arguments`（リテラルの JSON オブジェクト、キー数上限32）を追加。値の選択は制作 AI の意味判断、型の検査はコード。入口カードに引数 schema が無い入口への指定は `unexpected_arguments`、schema 不適合は `invalid_arguments`（検証は `z.fromJSONSchema`、未対応の schema 構文では `arguments_unchecked` 警告に留める）。省略時は入口側が task と資料から構造化する（モックの `entry-structures` 方針が既定）。`PlannedStep` と `StepExecution` まで値を運ぶ配線も通した |
| 結果の契約 | 完了した手順が後続へ渡す実体は、要約と host 発行の参照であり、output がある経路では入口の宣言に従う。採用できるのは `completed` のみ（従来どおり）。定義の `result` は自然言語の期待であり型ではない |
| 制作側の状態 | `src/contracts/authoring.ts` に `AuthoringOutcome`（ready / needs_input / unsupported）を追加。ready だけが検査と実行へ進み、ready の定義も必ず `checkDefinition` を通す。未解決の案を ready と偽らない |
| 版の記録 | `src/contracts/record.ts` に `DocumentRecord`（formatId、contractVersion、documentVersion、documentDigest、sourceRequestDigest、catalogVersion、revisionOf）と `CONTRACT_VERSION = "p0-1"` を追加。値はホストが計算して記録し、制作 AI は書かない |

補足: 版の記録モジュールは当初 `document.ts` という名前にしたが、`bench/mock/guard.test.ts` の DOM ガード（`/\bdocument\./`）が import パスの `document.` に一致して落ちるため、`record.ts` へ改名した。データの形は変えていない。

## 4. P0c への設計課題

- **モックの完了 output の合成方針（§1 の含意）**: command 入口について、モックが完了 output として何を合成するか（受領票形か、不透明な結果レコードか）を、受け渡しを採点する比較の前に決める。現行モックは `card.output` の schema から合成しており、ジョブ型の実態（ドメイン結果レコード）とは異なる。
- **agent-model の推論口**: P0d では Muse 自身が推論を担当する。`InferencePort` を、記録済みのエージェント出力で再生する adapter として bench に用意し、生成役にはケースの正解を見せない。利用量（トークン）は取得できないため null のまま記録し、費用は実測と呼ばない。
- ケース（`data/cases/`）、形式別 parser、部品カードの提示、採点器、`bench:format` / `bench:selection` の入口は引き継ぎ §6-3 のとおり。
