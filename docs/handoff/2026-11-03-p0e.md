## 2. 決定事項と推奨

### 2.1 採用形式 — 推奨: JSON を正とする（暫定）

3形式で差が無い以上、選定軸は「壊れにくさ」になる。JSON は重複キー・型・必須項目を機械で最も厳密に止められ、検査器も既に厳密リーダで固定済み。free-md は人が読みやすい反面、括弧構文など暗黙の約束が増え、弱いモデルでの崩れ方が読めない。md-yaml は中間。**最終確定は弱いモデルでの測定後**とし、それまでは JSON を正、他2形式は parser を残して比較可能性を保つ。

### 2.2 最小必須項目 — 推奨: 現行の定義形をそのまま必須の正とする

必須は request / steps / output と、手順の id / bundle / task / from / result。任意は arguments のみ。これ以上の削減（result の省略など）は、第2回で36/36が回っている現行形を変える理由がない。版の記録（DocumentRecord）と制作状態（AuthoringOutcome）は定義の外側の管理値として分離済み。

### 2.3 Router の採用範囲 — 推奨: 「候補の提示」までに留め、絞り込みには使わない

類似度だけでは top-1 が外れるケースがあるため、候補だけで部品を絞る使い方は根拠が弱い。当面の採用範囲は「候補を制作側への参考提示として渡せる」までとし、全部品提示との制作結果の比較（P0d 選択条件）は未実施のまま残す。本番 network（リランカ込み）での実測と、評価ケースと学習文の重なり確認が済むまでは、Router の数字を採用判断の主根拠にしない。

### 2.4 Eumenes 本体への接続方式 — 推奨: (b) 薄いホスト adapter

- (a) 本体の `pipelineDefinitionV1` へ変換して既存のパイプライン実行基盤に流す: 本体の永続化・再開・キャンセルに乗れるが、変換層が定義の意味を二重に管理し、instant の即答（summary で回答が返る）や research の ticket 引き継ぎを別形式へ写す作業が増える。
- (b) ホストが定義を読み、既存の子実行（ChildExecution / ChildResult）を直接呼ぶ薄い adapter: 本体は元々この形の子実行基盤を持ち、pipeline の StepExecution はそれに合わせて設計してある（P0a で実物を確認済み）。変換の二重管理がなく、instant は summary、command は完了結果の参照、という実際の受け渡しにそのまま対応する。
- 推奨は (b)。ただし本体側の変更を伴うため、着手は P1 の範囲で利用者が判断する。

## 3. 未実施・未測定（隠さない）

- 選択条件の比較（依頼文のみ／部分一致／Router 候補／全部品／正解部品で制作がどう変わるか）。bench:format は全部品提示の固定条件のみ実装済みで、カード集合を変える条件は未実装。
- 弱いモデル（対象モデル）での形式測定。推論経路が無いため未実施で、agent-model の数字で代用しない。
- 記述量（トークン数）の比較。tokenizer が無いため未測定。文字数で代用しない。
- Router 本番 network（Ruri リランカ込み）の実測と、評価ケースと学習文の重なりの確認。
- ケースの拡充（組み合わせ90件＋連携10件は P1 のデータ整備と併せて）。
- モックの完了 output の合成方針（受領票形のままか、不透明な結果レコードにするか）。現行は受領票形で、採点は配線だけを見ている（P0b 引き継ぎ §4）。
