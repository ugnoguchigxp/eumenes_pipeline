## 2. agent-model の推論口（P0b §4 への回答）

推論の担当は利用者の指示（2026-11-03）により Muse 自身。生成は bench の外で行い、`RecordedInference` は記録の再生だけをする。

- 記録は推論リクエスト（purpose + system + prompt）の digest で引く。digest が一致しない記録は使わず、記録が無いリクエストは明示的なエラーを返す（推測で埋めない）。
- 利用量はすべて null（取得できない値を 0 で埋めない）。記録される model 名は `agent-model` で、結果は agent-model の証拠として区別する。実モデルの受入とは呼ばない。
- parse の後段に P0b の `AuthoringOutcome` 検証をゲートとして置いた。parser の前段は未検証が仕様のため、たとえば「質問が空の needs_input」は parse を通っても authoring で落ち、セルの合否（passed）は scorer の内訳と authoring の両方で決まる。検証結果は trial の score 行（criterion `authoring`）に残る。

## 3. bench:format の約束

- 条件は固定: 形式（json / md-yaml / free-md）× 雛形1種（定型の指示 + 全提示カード、カード描画はテキスト形式で全形式共通）。**提示カードは24入口**（有効26件のうち ready 13 + partial 11。残り2件は session のため excluded で、提示しても検査で弾かれる）。条件を変えたら雛形の版を上げ、新しい run にする。
- 記録の置き場は `data/runs/format/<session>/`（`--session <name>`）の `requests/` と `recordings/`。1回の実行 = 作業 DB の新しい run（追記専用。途中まで用意して再実行しても終わった trial は書き換わらない）。
- セル（ケース×形式）の不足は黙って飛ばさない: 記録が無ければ request ファイル（caseId・形式・purpose・system・prompt・digest）を書き、trial は `interrupted` で記録し、集計の missing に数える。digest 不一致は `failed` で記録し、その記録は使わない。未充足のセルが1つでもあれば CLI は終了コード 1 で終わる。
- 集計は形式ごと・全体とも、fixture 依存ケース（`usesFixtureContracts`）とカタログのみのケースを分けて出す。分母は各段（parse / authoring / check / 状態 / 部品 / モック / 合否）ごとに実際に到達したセル数。

合成記録での実走（2026-11-03、session `p0c-synthetic`、3ケース×2形式=6セル）: scored 4（うち passed 2: prime-count/json の正常定義、vague-request/json の needs_input）、missing 2（記録を用意していないセルで request が生成された）。md-yaml は prime-count の部品選び間違いを bundles で落とし、stock-quote のアンカー付き YAML を parse で落とした。**これは配線の確認であり、モデルの成績ではない。**

## 4. Router adapter の扱い

- 使うのは検索層だけ: 部品カード → `cardPassages`（題名・要約・使う場面。カードに実例文は無い）→ transport で一括埋め込み → `closestSimilarities` + `rankBy`。会話の決定（`route()`）と学習済み best-v2 スコアラーは使わない。`RESOURCE_WORDS` のような語句加点も入れていない（plan §8）。
- transport は差し替え可能。テスト用は決定的な stub（文字 bigram の BoW。合成であり、順位は配線の証拠にしかならない）。live 用は環境変数 `PIPELINE_EMBED_URL` / `PIPELINE_EMBED_NETWORK` の両方が揃ったときだけ有効で、期待する応答の形は `bench/selection/live.ts` の冒頭に明記した。Provider の起動・停止・設定変更はしない。live のとき到達ガードはその endpoint への fetch だけを許可する。
- **この環境では live 設定が無い（両変数とも未設定）ため、Router 経路は未接続・未測定**。`bun run bench:selection` はその旨を表示して終わる。stub での実行は作業 DB に transport を `stub (synthetic)` と記録して行える。
- 候補の記録には network 名・モデル hash（埋め込み空間の artifactDigest）・取得時刻を必ず含める。評価ケースと Ruri の学習文の重なりを確認できるまで、Router 経路の数字を未見データでの精度と呼ばない（plan §9、骨格 §7）。

## 6. P0d の実施手順（agent-model の回し方）

1. 条件を固定する: 形式・雛形の版・カタログ版・ケース群・反復数を run の config に残る形で決める（雛形を変えたら版を上げる）。トークン数の比較（plan §10 段階1）に使える tokenizer が無いため、記述量の比較は未測定のままにする（文字数で代用しない）。
2. `bun run bench:format -- --session <名前>` を実行し、全セルの request を生成する（この時点では全セル missing でよい）。
3. 生成役（サブエージェント）が request ファイルだけを読み、対応する recording を `recordings/` に書く。生成役にはケースの `expected` を見せない。request に含まれるのは依頼文・提供資料・部品カード・形式の規則だけである。
4. 同じ session で `bench:format` を再実行する（新しい run として記録される）。digest 照合を通った記録だけが再生され、parse → authoring → check → モック → 採点まで通る。
5. Router の効果を測る条件は形式比較と分ける（plan §10）: 全件提示の基準条件と、Router 候補で絞る条件を別 run にし、候補の取りこぼしと選択の誤りを分けて集計する。live transport が必要なら、Provider の配備状態と network 名・モデル hash を利用者に確認してから行う（この bench から Provider には触れない）。
6. 途中で条件を変えた分は別実験として記録する。完了した試行の出力を消して同じ試行番号でやり直さない。
