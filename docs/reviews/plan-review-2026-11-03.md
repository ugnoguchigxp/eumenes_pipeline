## 照合した根拠

| 根拠 | 観測と適用範囲 |
| --- | --- |
| E1: コピー済みカタログSQLite | 有効26件中、binding参照あり17件・なし9件。17件の実行種別はcommand 13・instant 2・session 2。入力schemaの52参照はbuiltin、出力schemaの13参照はdomainで、型の実体は写しに含まれない。延べ参照数であり、実行可能性や異なる型の数ではない |
| E2: [現行パイプライン契約](../../../eumenes/api/domains/capabilities/contracts/pipelines.ts)・[構造検査](../../../eumenes/api/domains/pipelines/service/check.ts) | 現行は2〜8ステップで、引数・資料・extractと実行種別の制約がある。新しい3項目の記述と自動的に互換になる根拠はない |
| E3: [bundle登録とschemaの責務](../../../eumenes/docs/toolchain-extension.md) | bundleは複数の定義・binding等を持ち、builtin・domainのschemaはコード側にもある。bundleの文書登録元だけを実行部品の完成した契約とは扱えない |
| E4: [固定したRouter配布物のmanifest](../../vendor/router/manifest.json)とtarball内部 | SHA-256を照合。配布物内に語句による加点があり、`route()`にbest-v2は統合されていない。ソースの計画と実際の出荷内容を区別する必要がある |
| E5: [元の目的・作業規則](../../../eumenes/AGENTS.md)と本チャットの合意 | 部品内部を隠すこと、意味判断をLLMに残すこと、実行機構を重複させないこと、記述形式は比較して決めることを維持する |

E1は読み取り専用の集計のみを行い、会話・設定・秘密の内容は調べていない。E4の確認では、保存済みtarballを更新・再ビルドしていない。

## 修正した指摘

| 指摘 | 元の問題と影響 | 反映先と確認条件 |
| --- | --- | --- |
| R1: 実カタログの契約不足 | SQLiteにschemaの参照があっても型の実体がなく、旧形式の9件もそのままでは部品にできない。評価を開始できず、対象を黙って減らすおそれがあった | §4・P0aに取得元・対応可否の棚卸しを追加。対象集合と全26件への対応率を両方残す |
| R2: P0とP1の依存 | 比較に必要なvalidatorとモックをP1まで待つと、P0の比較で採用形式を決められない | §10をP0a〜P0eへ整理。bench用の試作と製品実装を分離し、P0の完了条件を統一 |
| R3: 短い定義から実引数への接続 | `task`・`from`と自然言語の`result`だけでは、型付き引数や複数入力の役割を確定できない | §5に入力の構造化・変換作業・結果契約の設計条件を追加。command、instant、複数資料、型付き変換で接続を示してから比較する |
| R4: 制作状態と実行状態の混在 | 情報不足、未対応、追加入力、文書の版を扱う契約がなく、未完成の案や古い結果を実行へ渡す余地があった | §3に制作状態・元依頼と変更依頼・正本・版の固定を追加。具体的な管理形式はP0で確定する |
| R5: bundleとRouterの粒度の違い | Routerのtoolchain IDをbundleと同一視したり、手順内でpipelineやsessionを選ぶと責務が崩れる | §4・§8に根拠のある入口対応、依存の版、候補の適格性、固定tarballを明記。Routerの最終選択への採用は未決のまま |
| R6: 形式比較の条件の差 | 修正の初期状態、JSONの制約付き生成、重複キー等の扱いが違うと、形式の効果を公平に測れない | §10に共通契約、初期状態別の修正比較、parser規則、生成経路の分離を追加 |
| R7: 費用と採点の偏り | 少数例、全件棄却、失敗の除外、正解の分解文、自己評価だけで有利な結論を出せる余地があった | §9・§10に診断・選定・最終評価の分離、正負例別の集計、失敗込みの費用、検索単体と通しの分離、採点の盲検化を追加 |
| R8: モックと資料の境界 | 「モックにする」という方針だけでは、複製したbindingから実ツールへ接続したり、資料内の指示を採用したりする経路が残る | §5・§10に許可された参照の解決、モックだけの実行口、実ツールへ到達しない検証を追加 |
| R9: 学習段階の依存 | P3に学習ありの結果を要求すると、後段のP4を先に実施する必要がある | §10のP3を基準測定と評価環境、学習後の測定をP4に変更 |
| R10: 再現・完了の記録 | P0の具体的な入口と保存物が曖昧で、設定変更や再実行で結果を比較できなくなる | §10に予定するscript、manifest・ケース・trialの記録と固定条件を追加。未作成のコマンドであることを明記 |

## 反復の経過

1. 契約とデータのレビュー: E1〜E3を照合し、R1〜R4、段階の依存を修正した。
2. 評価方法のレビュー: 費用、生成・修正の条件、データの漏れ、採点を点検し、R6〜R8を修正した。
3. 境界と再現性のレビュー: 版・候補の適格性・実行の隔離・成果物を点検し、R5・R10と関連する記述を修正した。
4. 3ラウンド後に進め方を俯瞰し、新機能を増やさず全体の整合性確認へ移った。P0の完了条件の表と詳細の食い違いを統一し、修正版を再確認した。

## 確認したことと、今回確認していないこと

確認したこと: 見出しの構成、JSON例の構文と参照順序、相対リンク、数値の根拠、SQLiteの整合性とchecksum、Router tarballのchecksumと該当実装、計画書の差分、実装済み・未実装の区別。これらは文書と根拠の確認であり、予定した機能の動作試験ではない。

確認していないこと: 各schemaの完全な抽出、26件すべての部品化、モックと評価器の動作、モデルの選択精度、JSON/YAMLの費用と品質、実ツール・Webの動作。今回の変更は文書のみなので、domain検証・E2E・モデル呼出しは実施していない。
