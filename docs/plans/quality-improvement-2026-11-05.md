## 実装内容と受入条件

### Q01 外部ファイルに依存しない単体試験

対象は `bench/tokens.test.ts` と必要な試験用補助処理である。既存の偽runnerと環境変数の差替え口を使い、一時ディレクトリに最小のtokenizer用ファイルと出所記録を作る。実モデル用のファイルをダウンロードして試験を通す方式は採らない。

存在、不在、不正な返答、計数失敗、出所未記録を各々確認する。fixtureによる文字数応答は配線試験と明示し、実tokenizerの計数値として報告しない。実tokenizerの確認は明示的な別実行に分け、通常ゲートに接続情報を要求しない。

受入は、`bun test bench/tokens.test.ts` の成功と、tokenizer設定を持たない新規作業コピーでの `check:all` 成功である。欠損時にnullを返す期待値と、外部到達を拒否するガードは維持する。工数Sは、既存の差替え口と2件の失敗箇所に変更を限定できるためである。

### Q02 JSON特殊キーと入力境界の修正

対象は `bench/formats/strict-json.ts`、`outcome.ts` と関連試験である。重複キー検出と深さ制限は再利用し、プロパティの安全な生成と自身が持つフィールドの参照へ直す。通常のJSONと同じデータになることを確認する。特殊キーを語句別に削除する処理は追加しない。

`__proto__`、`constructor`、`prototype`、エスケープで表した同じキー、入れ子、重複、境界の深さと長さを確認する。生成した小さいJSON値を標準 `JSON.parse` と比較する差分試験も使い、重複キー等の意図的な厳格さは別に検査する。継承されたstatusだけで状態が変わらないこと、fixtureの元データが変わらないことを確認する。

受入は特殊キーの保持、F03反例の解消、通常入力の互換性である。JSON復元とID正規化を有効にした経路にも同じ検査を適用する。配布外のbench内で解決し、`src/` のAPIを変更しない。工数Sは局所的な生成方法と判別方法の変更である。

### Q03 実行開始時の入力と採点版の固定

対象は `bench/format/run.ts`、選択実験のrun作成箇所、`bench/store/work-db.ts`、`bench/cases/` である。まず既存の `config_json` と `inputs_json` に版付きのmanifestを保存する方法を使い、新しいDBの列は共通機構で満たせない場合だけ追加する。

manifestはケース全体と各ファイルのdigest、ケース集合とsplitとgroup、カタログと契約、promptとparserとscorer、正規化等の条件、コードのcommitと未commit状態またはソースdigestを固定する。実モデルの識別と設定、検索のnetworkとモデルhash、入力schemaも記録する。正解は評価側にだけ保持し、制作側へ渡さない。

単なるhashに加え、元の入力を復元できるsnapshotまたは取得可能な保管参照を用意する。既存snapshotの読取り専用と照合方法を再利用し、同名のsnapshotを差し替えない。秘密や実会話を無断で保存しない。

受入は、ケース本文、正解、採点器、prompt、コードが変わる条件を別々に検出すること。過去runは分かる情報だけを示し、実行時の版が不明ならnullまたは明示した旧形式状態を返す。完了済みrunに後からdigestを追記して当時の記録に見せない。必要なDB移行は版を上げ、作業DBの複製で検証する。工数Mは複数CLIと旧run互換性に及ぶためである。

### Q04 依存関係と最終配送の構造評価

対象は `bench/cases/cases.ts`、`bench/scoring/score.ts`、関連試験、評価ケースの期待値である。既存の状態、選択部品、材料、mock実行の内訳を残し、評価側にだけ必要な依存と配送の制約を加える。

正解は作者が決めたstep IDの完全一致にしない。必要な役割同士の受け渡しと許容する解の組を表し、同じ入口を複数回使う場合も区別できる最小表現にする。役割の意味と許容解は人またはLLMが定義し、コードは確定した関係と参照だけを検査する。依頼の語句から必要な関係を製品コードが推測する処理は追加しない。

`finalArtifact` の既存の意味は採用済み出力の存在である。最終配送の別項目を導入し、`RunOutcome.delivered` に実際に含まれるホスト発行参照と照合する。型の分からない要約だけの出力を、文字列から画像や音楽と推測しない。検査不能は未確認として残す。

受入には、F01反例、誤った相手への配送、成果物の未配送、入口の重複、循環、不要操作、複数の妥当な分解を含める。期待した負例が落ち、妥当な別解は通ることを確認する。旧方式の `passed` と新しい構造・配送・充足の判定には異なるscorer版を使い、同じ精度として直結させない。工数Mは正解表現と採点互換性の設計を含むためである。

### Q05 独立した意味評価と正解の監査

対象は `bench/scoring/`、`bench/format/prompt.ts` の評価用指示、既存の `InferencePort`、`MuseExecInference`、記録再生口、Q14のClaudeとOpenAIの薄いAPI adapter、ケースの監査記録である。生成側の指示と情報提示を先に見直し、独立評価も同じ推論接続口を再利用する。新しい汎用エージェント基盤は作らない。

意味評価には、元の依頼、公開カード、候補の定義、観測された結果、出所を渡す。依頼の充足、部品の適否、担当の抜け、参照の役割、余計な作用、成果物の提示可能性をLLMまたは人が判断する。生成モデル名、形式名、条件名、費用を伏せる。正解やレビュー結果を制作・検索・mockへ逆流させない。資料内の指示を評価方針として扱わない。

自己採点だけで採用を確定しない。開発集合で独立した評価担当と人のレビューを照合し、不一致は理由と最終判定を記録する。doclingとdotsのようにカードと正解の意味が曖昧な場合は、カードの根拠と許容解を先に監査する。正解を変えた場合は新しいケース版とし、旧runを改変しない。

評価出力は項目ごとの判定、根拠、未確認点を持つ契約にする。評価不能、拒否、不正応答、時間切れを不合格や合格へ黙って変換しない。実モデルが不在なら、記録再生で配線だけを確認し、意味評価の正式受入は残す。

受入は、F01反例と誤選択を検出し、言い換えと妥当な別解を誤って落とさないこと。判定器の偽合格、偽不合格、不一致、未確認を開発集合で測り、許容水準を最終評価前に固定する。全件を生成履歴を共有しない独立した推論呼出しで判定し、Q14では両社の出力を両社の判定器へ同じ基準で提示する。自己生成側の判定だけで採用を確定せず、不一致と境界例は人が確認する。工数Mは評価契約と校正を含み、実推論の予算はQ14で別に確保するためである。

### Q06 証拠一式の保存と独立再生

対象は `bench/export/export.ts`、`bench/cli/export.ts`、`bench/store/` と関連試験である。既存の追記専用DBとexportを拡張し、可変の `summary.json` を必須証拠にしない。

runごとの保存物に、版付きmanifest、必要な入力snapshot、promptとschema、生成と修復と評価の生出力、そのdigest、状態遷移、採点の内訳、実測時間と取得できたusageを対応付ける。秘密を含む資料は保存許可に従い、安全な参照と保持期間を使う。実費やprovider usageが取得不能ならnullを保つ。元の出力を整形後の保存形で置き換えない。

exportでは実行時manifestと照合し、Q03のF02反例を拒否する。旧runは来歴の確認可能範囲を表示する。すべての整合性項目を終了コードへ反映し、同じrunの不一致を成功扱いしない。別runによるsummary更新は履歴上の差として区別する。

受入は、リポジトリの現在のケース、可変summary、元の作業DBに依存しない別の一時環境で再計算し、同じ構造判定と記録済み意味判定の集計が得られること。記録再生の一致と、実モデルを新規呼出しした際の揺れは分ける。ファイル改変、欠損、採点版の相違、全フラグ、修復前後、未完了runを確認する。工数Mは保存と再生の複数境界を扱うためである。

### Q14 Claude APIとOpenAI GPT-6 Lunaでの受入

対象は `bench/infer/`、`bench/format/run.ts`、実測用CLI、Q07の凍結manifestと新しい最終集合である。今回の利用者指定に基づき、直接APIによる検証を追加する。呼出しをMuseへ迂回させることは必須にしない。既存の `InferencePort` と共通のprompt、parser、authoringゲート、scorer、DBを再利用し、providerごとに異なる採点器や意味判断を作らない。

#### 接続先とadapter

| 経路 | 検証する接続 | model指定 | 役割 |
| --- | --- | --- | --- |
| Claude API | Anthropic公式のMessages API `POST https://api.anthropic.com/v1/messages` | 生成用と評価用を別設定にし、Haiku級など実際に利用可能な正式IDを開始前に固定する | 生成、修復、独立評価 |
| OpenAI API | OpenAI公式のResponses API `POST https://api.openai.com/v1/responses` | 生成の対象は `gpt-6-luna`。評価用modelも明示して固定する | 生成、修復、独立評価 |
| Muse | 既存の `MuseExecInference` | modelとproviderを記録 | 従来方式の対照または補助検証 |
| 記録再生 | 既存の `RecordedInference` | `agent-model`など記録した証拠種別 | オフライン配線と再計算 |

GPT-6 Lunaの公式model IDは `gpt-6-luna` で、Responses APIとStructured Outputsの対応を確認した。ユーザーの「Luna 6.0」はこのモデルとして扱い、非公式な別名を作らない。[OpenAIモデル情報](https://developers.openai.com/api/docs/models/gpt-6-luna)

実装は、例えば `bench/infer/anthropic-api.ts` と `openai-api.ts` に閉じた薄いadapterと、その差替え可能な通信処理にする。ファイル名は予定である。`src/` にAPIキー、provider設定、SDK、HTTP依存を持ち込まない。既存のfetchとZodで足りる範囲を先に確認し、公式SDKの採用が実装や互換性を改善する場合だけ、7日ルールと固定版に従ってdev依存へ追加する。両方式を重ねて実装しない。

生のAPI呼出しと採点を分離するため、共通の実測入口 `bench:infer` を追加する計画とする。既存のリクエスト生成を再利用し、選択した `InferencePort` へ当該requestだけを送り、API呼出しrunとproviderの証跡をQ03のmanifestで記録する。再生用の出力は既存の `{promptDigest, output}` と互換にし、provider情報は別の版付きmanifestに保持する。生成時のAPI証拠と、採点時の記録再生という実行方式を別項目にし、APIの出力を `agent-model` の成績として保存しない。由来を照合できない記録を実APIの証拠へ昇格させない。生成runと採点runを紐付け、オフラインの再採点がAPIを呼び直さないことも受け入れる。

同じpromptに対するprovider別、model別、条件別、反復別の出力は異なるsessionへ保存し、既存のpromptDigestによる記録を上書きしない。比較では同じケースをrun間で対応付ける。再生のdurationやusageをAPI生成の実測値として使わず、生成runに記録した時間とprovider usageへ遡って集計する。

`InferenceRequest` のsystemとpromptを、それぞれのAPIの指示と入力に機械的に写像する。新しい呼出しではケースごとに履歴を分離し、リポジトリのファイル、AGENTS、個人文脈、他ケースや正解を読み込ませない。APIへ送るのは許可された依頼と材料、公開カード、当該工程の指示だけとする。組込みツール、web、file search、MCP、コンピューター操作を有効にしない。予期しないtool呼出しが返っても実行しない。

#### モデル設定と比較条件

生成と評価のprovider、要求model ID、返却model ID、APIの版、clientまたはSDK版、出力上限、reasoningやthinking等の設定、出力schema、処理tier、キャッシュ条件をrunへ保存する。対応しない設定は無効化して記録し、両社で意味の違うパラメータを同じ値にしただけで同条件と呼ばない。別modelへの自動fallbackは行わず、失敗をその条件の結果として残す。

`gpt-6-luna` のように日付付きの別snapshotが取得できない場合は、実行日時と返却model情報、取得できた識別情報を残す。確認できないモデルhashやbackend版はnullとし、長期間不変なモデルだと断定しない。

比較を次の条件に分け、Structured Outputsによる構文安定化と、モデルの分解や選択の能力を混同しない。

| 条件 | 両社で固定すること | 判定 |
| --- | --- | --- |
| 通常生成 | 同じ依頼、公開カード、指示の内容、JSON生成形式。providerのschema強制は使わない | 生のparseとauthoring、構造、意味を採点する |
| schema強制 | 同じ正本の出力契約と、明示したprovider向けI/O表現 | 対応可否と構文安定化を通常生成とは別に測る |
| 修復 | 同じ機械的失敗の通知と上限1回の修復 | 修復前後と追加推論を別に報告する |

OpenAIでは `text.format`、Claudeでは `output_config.format` による構造化出力を公式仕様で確認する。両社のJSON Schema対応範囲は実装時に照合し、正本の制約を黙って削除しない。必要ならトップレベルのenvelope等、I/Oに限る写像を明示する。正本のローカル検査は常に実施し、対応できないschema強制条件は非対応として残す。通常生成へ黙って切り替えた結果を同じ条件へ混ぜない。[OpenAI構造化出力](https://developers.openai.com/api/docs/guides/structured-outputs)・[Claude構造化出力](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)

Claude生成とLuna生成の両方に、ClaudeとOpenAIの同じ2系統の評価を適用し、生成providerと条件名を伏せる。自己生成側と別provider側の判定を個別に保存し、一致だけで正しさを保証しない。Q05で人の判定との校正を行い、不一致と境界例を人が確定する。生成と判定を同じ会話履歴へ入れない。評価モデルの差による偏りと、生成モデルの差を分けて報告する。

#### 通信制限とAPIキー

認証は実行プロセスの環境変数から受け取り、次の優先順にする。providerの認証形式への接続に必要な小さい設定処理としてbench内に閉じ、LLMの意味判断と分離する。

| provider | 利用者の既存設定を優先 | 互換用の代替名 | adapterへの渡し方 |
| --- | --- | --- | --- |
| Claude | `CLAUDE_API_KEY` | `ANTHROPIC_API_KEY` | 選択した値を認証引数または正規の認証headerへ明示して渡す |
| OpenAI | `OPEN_AI_API_KEY` | `OPENAI_API_KEY` | 選択した値をclientの `apiKey` または正規の認証headerへ明示して渡す |

両方の名前が存在しても、上表の利用者指定名を優先する。SDKの標準変数名の自動検出だけに依存せず、別名へのexportや `.env` へのコピーを求めない。キーの値、長さ、先頭末尾、digestを診断へ出さず、利用した変数名と設定有無だけを確認する。空または空白のみの値は未設定として扱う。

利用者のMacでは `~/.zprofile` を設定の正本とする。ターミナルやCIが環境を継承していれば、そのまま使用する。GUIや既に開いていた実行環境へ継承されていない場合は、プロジェクトのディレクトリから `/bin/zsh -lc` のログインシェル経由で起動する。API adapterや配布ライブラリが `.zprofile` を読み取って解釈したり、毎回の推論でsourceしたりしない。ログインシェルで一度環境を整え、その子のbenchプロセスへ渡す。CIには同じ名前のsecretを注入し、Mac固有のprofileファイルを要求しない。

実装予定のコマンド例を次に示す。`bench:infer` は現時点では未実装であり、session、予算ファイル、Claudeの正式model IDは実行時に指定する。キーをコマンドへ書かない。

```sh
# プロジェクトのディレクトリで実行する。山括弧内は実際の値へ置き換える。
/bin/zsh -lc 'exec bun run bench:infer -- --provider openai --model gpt-6-luna --session <session> --budget <budget-file>'
/bin/zsh -lc 'exec bun run bench:infer -- --provider anthropic --model <claude-model-id> --session <session> --budget <budget-file>'
```

キーが無い場合は不足している設定名とログインシェルからの起動方法を示し、有料呼出し前に停止する。設定不足を記録再生へ自動で置き換えない。コード、CLI引数、ケース、manifest、prompt、ログへキーを保存しない。利用者の `.zprofile` 自体はこの作業で変更しない。

2026-11-05の計画作成時には、明示的な `/bin/zsh -lc` の子プロセスで両変数の存在を真偽値だけで確認した。通常の実行プロセスでは未継承だったため、ログインシェル経由を確認手順に含める。この確認ではAPI通信、認証の成功、モデルへの利用権限、課金を検証していない。

到達ガードを最初に設置し、選択したproviderのHTTPS接続先と必要なAPIパスだけを許可する。URLは文字列の前方一致ではなく解析後のscheme、host、port、pathで照合する。requestのmethodとbodyの契約も通信処理で検査し、リダイレクトと任意のbase URLを拒否する。SDKを使う場合は差替え可能なfetchをガード経由へ接続し、SDKがガードを迂回しないことを試験する。

新しい許可は今回指定されたAPIの検証に限定する。未知の互換API、proxy、外部ツール、記録されたURLやモデル出力に従う追加通信を許可しない。現行AGENTSのMuse限定規則とガード説明は、API adapter実装時にこの利用者指定を根拠として同時に更新する。通常の単体試験と `bench:verify` は引き続き外部通信0件とする。

#### 終了状態と記録

HTTP成功だけで完成扱いにしない。OpenAIの応答状態と拒否や不完全な出力、Claudeの `stop_reason` と拒否、出力上限、空応答を別々に判定する。APIの拒否を、依頼に対応する部品がないという `unsupported` の正解に変換しない。予期しないblock、schema不適合、途中で切れたJSONは、記録した失敗として共通ゲートへ渡す。[Claude終了理由](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)

request ID、response ID、開始と終了時刻、待機と再試行を含む時間、providerが返したusage、エラー分類を試行と紐付ける。OpenAIのcached token、reasoning token、Claudeのcache読込みと作成などは、生の項目を保持してから共通欄への写像を文書化する。取得できない数値を0にせず、API呼出し回数から内部のモデル呼出し数を推定しない。HTTP試行数と `InferenceUsage.calls` は別の値として扱う。

#### 再試行と費用

SDK等の暗黙の自動再試行は無効化し、明示的な共通方針へまとめる。認証、権限、課金不足、存在しないmodel、非対応schemaは条件を変えずに再試行しない。429や一時的な5xxは、公式エラーとrate-limit情報を確認し、事前に固定した回数、総期限、待機、予算の範囲だけ再試行する。タイムアウト後も課金済みの可能性を残し、成否不明を費用0にしない。通信の再試行と内容を直す修復は別の試行として記録する。[Claude APIエラー](https://platform.claude.com/docs/en/api/errors)

開始前にprovider別と全体の上限を設定する。制作、修復、両社のjudge、dev校正、疎通試験をすべて含め、各呼出し前に残り回数、入力と出力上限、deadlineを確認する。例えば40ケース、3反復、2生成providerなら制作だけで240呼出しとなる。評価と修復の費用をこの件数へ隠さない。

事前予算の見積り、usage、実際の課金は区別する。価格表の確認日時、通貨、tier、キャッシュ等の課金条件を固定し、見積りを実測費用欄に転記しない。個別試行の実費を取得できない場合はnull、取得できる請求集計はその集計粒度で報告する。上限に達したら部分完了として保存し、新しいrunなしで継続しない。どちらかのAPIの失敗を他社の呼出しで隠さない。

#### 実行順と受入

1. 実APIキーなし、通信差替えの単体試験で、両社の正常、拒否、出力上限、空応答、不正block、401、403、429、5xx、タイムアウト、取消、キーのマスク、予算停止、接続先とリダイレクトの拒否を確認する。偽の環境変数を渡し、指定名だけ、標準名だけ、両方、欠損、空白を検査し、利用者指定名の優先と不足時の通信0件を確認する。
2. 共通 `InferencePort` から記録、再生、共通採点、exportまでを結合し、要求と返却modelの不一致を検出する。`src/` の公開APIと配布依存を増やしていないことを検査する。
3. 実行可能なキーと予算を準備した環境で、正解を含まない合成の疎通入力を各社へ最小件数だけ送る。利用可能性、実model ID、API契約、usageの取得を確認する。
4. devで正常、拒否、機械的失敗、修復、意味的不一致を確認し、閾値、候補方式、judgeの校正、予算、比較条件を凍結する。
5. 新規の最終集合で両社を同じ課題に対して実測する。初期案は新規40ケース、独立group、事前固定した3反復とする。正式な件数と反復、実行順、比較方式はdevの分散と予算を見て開封前に確定し、途中成績を見た追加や条件変更は行わない。
6. モデル間の差を同じケースごとの対として集計し、構文、authoring、構造と配送、意味充足、過剰確認、未対応判定、修復前後、所要時間、usage、実費を分けて報告する。

正式な受入には、Claude APIとOpenAI APIの `gpt-6-luna` の両方について、新規の実呼出し結果と独立評価の証拠が必要である。どちらかの設定やモデル利用権限が未成立なら、その条件は未実施として残す。ready、partial、fixture依存を混ぜず、カタログ対応率は有効26件を分母にする。別model、別network、通常生成とschema強制の成績は混ぜない。

受入は事前の合否基準と予算への適合であり、87.5%など旧scorerの数字を新scorerの合格閾値へ転用しない。旧生成物を新scorerで再評価する比較と、API経由の新規生成は別runで記録する。小さい件数の改善は件数と不確実性を示し、単独の平均値だけで採用しない。工数Lは2社のAPI契約、盲検評価、反復、費用管理を含むためである。

### Q15 本体の実経路への接続と検証

本体側へ変更する明示的な依頼がこの作業の開始条件である。開始前に既存のadapter検証ブランチと現行本体を読み取り、再利用できる実装と現在の契約との差分を確認する。未保存の他作業や本体mainの差分を変更しない。

対象は本体の `api/application/pipelines/`、既存のtoolchain実行port、vendor、関連する既存画面である。`PipelineHost`、`InferencePort`、`ComponentRecord` を既存の子実行、LARM、登録済みカタログへ写像する。新しい実行器は作らない。`prepare`、`execute`、`adoptInTransaction` の既存経路と権限、確認、期限、予算を使う。

本体では版を起動時に再解決する既存規則と、計画が固定した版との扱いを明記する。勝った版と理由を記録し、取消、期限後の結果、参照の所有とdigest、必要な確認を検証する。commandの受領票schemaと完了結果の契約を区別し、モック用の受領票照合を実ホストへそのまま持ち込まない。

許可されたテスト用資源で、実ツールを使う短い依頼と複数手順の依頼を完遂する。少なくとも資料の受渡し、成果物の最終提示、途中失敗、確認待ち、取消、期限、成否不明、権限拒否、再実行時の重複防止を確認する。副作用はホストの既存確認とテスト資源の範囲に限定する。

受入には `pipelines`、`capabilities`、`agent-runtime`、`dialogue` の対象domain検証、vendor整合性、公開契約のconsumer確認、対象ブラウザー試験を含める。画面がない場合は未実装範囲として残す。必要な常駐環境の準備は利用者に依頼し、自分で起動停止しない。工数Lは別リポジトリと実ツールと画面の接続を含むためである。

### Q16 導入と診断と更新の利用確認

対象は利用手順、SDK例、既存のrunとexport、Eumenesの既存画面と診断導線である。新しい画面基盤や二つ目の状態台帳は作らない。状態の正本は既存の永続記録とし、画面と説明はそこから導く。

初見の担当が、依存導入、サンプルの検査、未知入口や引数エラーの診断、runの比較、配布物の更新、中断後の状態確認、旧版へ戻す操作、不要な導入の除去まで実施する。内部実装名を通常の利用者向けフローへ出さず、何が成功し何が不足したかを説明する。

受入は、作成者の口頭補足なしに代表作業を完了し、確認待ちと部分成功を誤認せず、エラー位置と必要な次の行動を把握できること。SDK担当と画面利用者の対象作業を分けて観察する。小さい画面変更も、対象となる既存のアクセシビリティと操作手順を確認する。工数Mは導入から更新と復帰までを通すためである。

### Q17 同一基準での技術品質再評価

対象は新しい評価台帳と受入証拠である。基準台帳と同じrubric、profile、30項目、重み、適用範囲を保ち、実装後の明示的source snapshotと再現archiveを固定して評価する。作成者と独立した検証担当による確認が可能なら用い、同じ担当が行う場合は別の反証工程と明記する。別チャットや外部担当へ勝手にメッセージを送らない。

各指摘を再現し直し、解消、新規問題、未確認を区別する。4の評価には、正常系の成功だけでなく、重要境界、負例、別の説明を排除する独立照合が必要である。計画上の目標値を実施結果の欄へコピーしない。

受入は、採点スクリプトによる構造と参照と計算の検査に加え、根拠が評価水準を満たすことの手動点検を終えること。80点に届かなければ未達項目と根拠を報告し、要件やテスト期待値、対象範囲を弱めずに残作業を更新する。工数Mは証拠の再照合と反証を伴うためである。

### Q18 利用効果と継続運営の確認

将来性の未確認項目は、コード変更だけでは埋まらない。対象は実利用の同意と記録、共通課題での比較、運営と展開の判断資料であり、新しい利用者データ収集は許可後に行う。

同じ依頼を従来の手動組合せまたは現行の適切な経路で行った場合と比較する。再利用toolchainを作る旧Studioと一回限りの手順を、そのまま同一課題として比べない。完了までの時間、修正回数、充足、失敗時の復帰、利用者の負担、実費を対応付ける。単純なケースは既存の直接実行で足りるという反証条件も含める。

試行案は、利用担当2名程度、実依頼20件程度で初期の使いにくさを確認し、その後4週間程度の継続利用を観察する。参加者、件数、期間、保存可能な情報、費用は開始前に確定する。少人数の結果を市場全体の需要と解釈しない。内部用途に適した費用対効果を優先し、売上や市場規模を推定して点を埋めない。

保守責任者、代替担当または引き継ぎ方法、モデルと依存更新の予算、障害時の対応、証拠の保持期間を決める。専門的な新規性は既存方式との差分と効果で評価し、既知技法で足りる場合は低い新規性評価を受け入れる。隣接分野への展開は、同じ核が役立った実例と費用が得られてから判断する。

受入は、効果、継続利用、導入負担、維持資源、代替案に対する選択理由を事実に基づいて評価できること。利用されなかった、価値が小さかった結果も保存し、必要なら規模を縮小または統合する。技術品質80点と将来性の高得点を同義に扱わない。工数と日程は、協力者と環境と観察期間を確定してから決める。
